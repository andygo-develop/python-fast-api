## Context

See `proposal.md` — Why. Three constraints shape the approach.

The schema currently exists twice: `Base.metadata.create_all()` in the lifespan builds it for the
running app, and again in `tests/conftest.py` for the suite. Introducing migrations means deciding
which of those two the migrations replace. The answer here is deliberately "only the first" — the
suite keeps building from metadata, which was chosen explicitly and is revisited under Risks.

The database is PostgreSQL 18 in development (set through `.env`), while SQLite remains the code
default and is what the test suite runs on. Migrations must therefore be authored to work on both:
SQLite has no general `ALTER TABLE`, so anything beyond adding a column requires a table rebuild there,
even though PostgreSQL would accept a plain `ALTER`.

The sign-in form change is small in code and disproportionately large in blast radius, because
`OAuth2PasswordRequestForm` is what ties the endpoint to Swagger's Authorize flow.

## Goals / Non-Goals

**Goals:**

- One authority for schema, applied by an explicit command, with a reversible history.
- Migrations that target whatever `DATABASE_URL` the application itself would use, so the two can
  never diverge.
- A repeatable development dataset that is safe by construction — it cannot be created in a deployed
  environment even by accident.
- A sign-in contract whose published schema is exactly what the server reads.

**Non-Goals:**

- Async migrations. The app is sync throughout (phase 1, Decision 1); Alembic runs sync and there is
  no reason for it to differ.
- Multi-database or multi-head migration topology.
- A general fixtures framework. Seeding covers users because users are what exist.
- Preserving OAuth2 password-flow conformance. The endpoint stops being a conformant token endpoint;
  that is the accepted cost of the chosen strictness.

## Decisions

### 1. Alembic, in a `migrations/` directory

Alembic is SQLAlchemy's own migration tool and the only serious option for this stack. Resolved as
1.19.1 on Python 3.14, pulling one new transitive dependency (`mako`).

The migration environment lives in `migrations/` rather than Alembic's default `alembic/`, with
`alembic.ini` at the project root. The directory name says what it holds rather than which tool
produced it, and the tool is already named by `alembic.ini` beside it.

### 2. `env.py` reads the URL from `Settings`, not `alembic.ini`

`alembic.ini` ships with a `sqlalchemy.url` key. Leaving a URL there creates a second place the
database is configured, and the two drift the first time someone changes only one — migrations then
build a schema in a database the app never opens.

Instead `env.py` imports `get_settings()` and sets the URL from `settings.database_url`, and
`alembic.ini` leaves the key empty. This is what makes the spec's "Migration target follows
configuration" requirement true by construction rather than by discipline.

`env.py` also imports the models module so `target_metadata = Base.metadata` is populated —
autogenerate silently produces an empty migration if the models were never imported.

### 3. `render_as_batch=True` for SQLite compatibility

SQLite cannot `ALTER TABLE` beyond adding a column, so Alembic's batch mode — copy to a new table,
move the data, swap — is required for anything else. It stays enabled even though development now runs
on PostgreSQL: the setting is inert on engines with real `ALTER` support, and SQLite is still the code
default and the test suite's engine, so a migration must not be authored in a way that only PostgreSQL
can apply.

### 4. Baseline migration matches the current model exactly; existing databases are stamped

The first migration creates `users` with precisely the columns `app/users/models.py` declares today.
That makes it a true baseline: a developer whose `app.db` was already built by `create_all()` runs
`alembic stamp head` to record that the schema is current, rather than migrating a schema that
already matches and getting a duplicate-table error.

*Alternative considered:* an empty initial migration followed by an autogenerated one. Rejected — it
records the `users` table as if it were added later, which misrepresents the history for no benefit.

### 5. `create_all()` leaves the application entirely

The lifespan stops touching the schema. This is the point of the change: while both mechanisms exist,
starting the app can paper over a migration nobody ran, and the failure surfaces later as a column
that exists in one environment and not another.

The consequence is intentional and worth stating plainly: **an unmigrated database now fails at the
first query rather than being silently repaired at boot.** That is the desired behaviour — a loud,
early failure with an obvious remedy.

### 6. Seeders are Python functions, idempotent by lookup

`app/db/seeds.py` holds a declarative list of users to create and a `run_seeds(session)` that, for
each, looks the username up and skips it if present. Idempotence comes from the lookup rather than
from `INSERT OR IGNORE`, so it behaves identically on SQLite and Postgres, and the command can report
exactly what it created versus skipped.

Seeding calls `UserService.create_user`, the same path the CLI and any future registration endpoint
use, so seeded users are hashed identically to real ones and no second creation path exists to drift.

*Alternative considered:* seeding from an Alembic data migration. Rejected — it welds test data to
schema history, runs in every environment including production, and cannot be re-run selectively.

### 7. The environment guard is checked in the command, before any write

`seed` reads `settings.environment` and exits non-zero on `staging` or `production` before opening a
transaction. Checking first means a refused seed cannot leave a partial write behind.

The guard is an allow-list in spirit: it permits `local` and `test` and refuses everything else, so a
future environment name added to `Settings` is refused by default rather than accidentally permitted.

### 8. `SignInForm` with `extra="forbid"` replaces both the OAuth2 form and the blank-field dependency

```python
class SignInForm(BaseModel):
    model_config = ConfigDict(extra="forbid")
    username: Annotated[str, Field(min_length=1)]
    password: Annotated[str, Field(min_length=1)]
```

declared as `Annotated[SignInForm, Form()]`. Form models are supported from FastAPI 0.114.0, and
`extra` defaults to ignoring unknown fields, so forbidding them is an explicit opt-in — confirmed
against the 0.141.1 manuals.

This deletes `get_sign_in_form` outright. That dependency existed only to turn blank strings into a
422, because `OAuth2PasswordRequestForm` accepts `""`; `min_length=1` now produces the same 422
natively, from Pydantic, with a properly shaped error body. One less hand-built
`RequestValidationError` to keep in step with FastAPI's own error format.

**This breaks the Swagger Authorize button**, which always posts `grant_type=password` along with the
client fields and will now receive `422 extra_forbidden`. That is the accepted, requested trade-off.
`/docs` remains usable for calling the endpoint directly — only the Authorize shortcut is lost, and
`README.md` must stop advertising it.

## Risks / Trade-offs

- **Migration drift is not caught by the test suite** → Tests keep building from model metadata, so a
  migration that disagrees with the models passes CI and fails in a real environment. Deliberately
  accepted for suite speed. Mitigation: `uv run alembic check` reports metadata-versus-migration
  divergence and is documented as the step to run after changing a model. It is a discipline, not a
  guarantee — the moment that discipline slips, the drift test rejected here becomes worth revisiting.
- **The Authorize button stops working** → Accepted and requested. The risk is that the loss is
  discovered by a developer rather than read in a document, so the README change is part of this
  change, not a follow-up.
- **An unmigrated database now fails at request time** → By design, but it is a new failure mode for
  anyone who currently just runs the app. Mitigation: README setup steps put `alembic upgrade head`
  before the first run, and the failure names a missing table, which is self-explanatory.
- **Seed users have published passwords** → A seeded account reaching a deployed environment is a real
  compromise. Mitigation is the environment guard plus the fact that seeding is never invoked
  automatically — no lifespan hook, no migration, only an explicit command.
- **Rejecting extra fields breaks unknown third-party clients** → Nothing outside this repository is
  known to call the endpoint, so the blast radius is believed to be zero; if that assumption is wrong,
  the symptom is a sudden 422 on requests that previously succeeded.
- **SQLite batch mode changes how migrations execute** → Table rebuilds are not free and behave
  differently from a real `ALTER` under concurrent access. Not a concern at current scale, and the
  alternative is migrations that simply fail on the default database.

## Migration Plan

1. Add Alembic and the baseline migration while `create_all()` is still in place — nothing breaks yet.
2. Existing databases: `uv run alembic stamp head`. Fresh ones: `uv run alembic upgrade head`.
3. Remove `create_all()` from the lifespan once the baseline exists, so there is no window in which
   neither mechanism builds the schema.
4. The form change is independent of the above and can land in either order.

Rollback: revert the commit and delete `app.db` if it was stamped, or `alembic downgrade base`. No
deployed environment exists, so no coordinated rollout is needed.
